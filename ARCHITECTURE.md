# Architecture

## Phase 7 protected embedding/deployment

One protected Node 24 service still serves the Vite build and authenticated same-origin APIs over a reviewed HTTPS ingress, using private durable local SQLite payload storage. The prepared multi-stage Dockerfile pins a verified Node 24 image digest, runs non-root and excludes development/test services and secrets. VM Caddy/systemd examples are preparation only. Default listener stays loopback; an explicit validated `TPM_BIND_ADDRESS=0.0.0.0` supports protected container/PaaS ingress. One instance is supported; serverless ephemeral disks/network-shared SQLite are unsuitable without a reviewed adapter change.

The root/sign-out access gates are the only public app HTML and contain no maintenance data, tokens or identity claims. Anonymous app assets/API remain denied. Authorization is initiated in a user-opened top-level tab, never redirected through a Google iframe. CSP still defaults to deny framing; exact HTTPS ancestors require operator review. The authenticated-tab fallback is the same dashboard, with the existing Google Site as launch point.

Google Workspace mode requires canonical Google issuer, approved exact domain, private confidential web-client secret file and existing subject/role allowlist. Signed `hd`/verified-email checks supplement issuer/audience/PKCE/state/nonce/expiry. Sessions bind provider/domain and invalidate on policy change. Private key/role/identity secret-file permissions are checked at startup. No raw Google token is persisted/returned. No live company provider has been configured or certified here.

Data & Settings presents four stable accessible panels without changing data-access/domain layers. A consistent operator-only SQLite ciphertext backup tool removes ephemeral auth/staging state from the backup, validates private paths, refuses overwrite and has no HTTP endpoint. Backups/key recovery and hosted acceptance remain operator responsibilities. See docs/HOSTING_OPTIONS.md, docs/GOOGLE_WORKSPACE.md, docs/GOOGLE_SITES.md, docs/PRODUCTION_CHECKLIST.md and ops/README.md.

## Current Phase 6 architecture

The implemented flow is React → authenticated same-origin Node HTTP API → shared normalized CSV parsers/domain rules → AES-256-GCM encrypted SQLite payloads on private durable disk. A single Node 24 instance is supported. `server/index.ts` is bundled to `build-server/index.mjs`; production serves both protected app assets and protected data endpoints. Vite is for synthetic development only. The synthetic OIDC test provider is excluded from the production entrypoint/bundle.

`WorkspaceProvider` coordinates one selected Demo/CSV work-order source across all six sections and verified same-account vendor/property catalogs. Page filters remain independent. Managed selection is reauthorized server-side; source/identity/role changes reset source-bound child state. Authentication loss clears cached operational datasets even while Demo is selected. Browser localStorage/sessionStorage never persist operational data, identity tokens or drafts.

`server/auth.ts` implements OIDC authorization code + S256 PKCE, state/nonce, discovered allowlisted endpoints/JWKS, signed token validation and an immutable-subject server role allowlist. Session cookies are HttpOnly/Secure/SameSite=None in production; CSRF tokens plus exact Origin checks protect writes. Every API request rechecks local role membership. Administrators manage sources, imports, configuration, retention and audit; viewers receive normalized records with vendor email/phone withheld. No proxy identity headers are trusted. Access is single-firm, not per-property.

`server/management.ts` stages bounded previews with actor/expiry/source revision/dataset revision binding, commits atomically and keeps stable source/account-scoped IDs. A mapping/content digest makes repeat imports idempotent without claiming a new observation. Snapshot mode archives absent records; upsert carries disclosed last-known rows and disables comparable-snapshot history. Original mapped cells are encrypted server-only; unmapped columns are discarded. Namespace records include sources/settings, staged imports, observations, record archives, original mapped values, import history, audit and sessions. Configurable retention expires data rather than silently retaining it forever.

`server/delivery.ts` processes private filesystem `*.ready.csv` files only after a reviewed mapping has successfully imported, an approved source schedule exists, and server operator configuration enables the private inbox. Gates default off. Private permissions, bounded UTF-8 reads and symlink rejection apply; failed validation retains the successful dataset and the input for operator review. This processes delivered files, not Rentvine report generation. One scheduled dataset per source is currently supported.

`server/integrations/rentvine.ts` is an intentionally unavailable typed read adapter. No Rentvine endpoints, credentials, live requests or write operations are implemented. Server API configuration rejects activation pending ownership approval and verified external documentation. Production OIDC/storage secrets use private server mounts, never browser variables. See [deployment/security guide](docs/DEPLOYMENT.md), [CSV route](docs/CSV_ONLY.md) and [API route](docs/API_ROUTE.md).

The earlier phase sections below are historical where they describe session-only persistence or Overview's independent demo; Phase 6 supersedes those limits. Actual protected hosting/Google Sites compatibility still needs real-environment testing.

## Separation of responsibilities
React + TypeScript + Tailwind frontend → normalized repository interface → selected adapter (synthetic fixture, CSV, optional server-side Rentvine). Domain selectors and business rules are independent of adapters and UI. GitHub holds source and sanitized fixtures only. Use a protected hosting environment for operational data; a public static demo may contain synthetic data only.

Proposed code organization: src/app (routing/layout), src/components, src/features (one directory per tab), src/domain (types/rules/selectors), src/data (repository/adapters/validation), src/config (public validated settings), and server/ (authentication, authorization, persistence and future source integration). This layout is now implemented; the phase sections below record its earlier proposed state.

## Repository contract
Define getSnapshot(), getDataHealth(), previewImport(input, mapping, scope), commitImport(previewId), and getComparableChanges(snapshotId). These are internal application method names, not HTTP routes or Rentvine endpoints. Imports are available only to authorized importers. All adapters return DATA_SCHEMA.md contracts and capability/coverage metadata. UI never parses raw Rentvine payloads or contains source credentials. Capability gaps produce unavailable states rather than guessed values.

## CSV release
For isolated local evaluation, synthetic or approved redacted CSV data may be parsed in memory with explicit session-only persistence. A shared operational deployment needs authenticated server-side validation, protected storage, importer authorization, and current/previous snapshots. Do not persist sensitive CSVs in localStorage, public assets, service-worker caches, Git history, build artifacts, or analytics tools. Choose and document retention and cleanup before enabling real data. Stage imports atomically; protect against simultaneous commits with version checks.

## Optional Rentvine integration
Do not enable until official current documentation and account access establish the required read operations, authentication, field availability, pagination, limits, and permitted scopes. Do not invent endpoint paths or reuse administrator/integration credentials. Use a dedicated least-privilege read-only identity with account-owner approval; if suitable permissions are unavailable, remain on CSV. The server allowlists verified read operations and fields, rejects arbitrary proxy URLs/methods, handles pagination, bounded retries/backoff, rate limits, and refresh failures, and sanitizes payloads before storage. Browser code cannot call Rentvine directly with credentials. API responses pass the same normalization and rule validation as CSV.

## Protected Google Sites embedding
Google Sites is a portal, not an authorization boundary for the embedded app. Authenticate and authorize each app/data request independently, including when the app URL is opened directly. Restrict Sites membership as an additional layer. Choose a hosting/auth provider that supports the required protected iframe behavior; do not assume Google Sites supplies user identity to the app.

Use HTTPS, role-based access (viewer, importer, administrator), minimal sessions, and server-side authorization. Configure CSP frame-ancestors for the verified portal ancestor origins after testing the real embed chain; never use a blanket wildcard. Align host framing headers without weakening unrelated protections. Use exact CORS origins only where needed; CORS is not authentication. Protect stateful import/config actions against CSRF.

Test third-party-cookie restrictions, login redirects, session expiry, logout, and mobile in the actual iframe. Keep credentials/tokens out of URLs, postMessage payloads, and localStorage. Validate postMessage origins if resizing is implemented. If protected iframe authentication cannot work reliably, provide an authenticated “Open dashboard” link instead; never make data public to force embedding.

## Security and privacy
Restrict vendor contact details by role and minimize tenant information. Do not collect tenant contact details or access codes for this product. Redact free text before preview/storage. Use transport and storage encryption, audit imports/configuration without raw payloads, validate file sizes/content, escape displayed values, and allowlist external Rentvine links by verified HTTPS host. Logs, errors, telemetry, screenshots, fixtures, and tests must be sanitized. Do not install session-replay tools that capture operational data.

Ignore .env and local overrides (except .env.example), real imports, snapshots, and sensitive artifacts in Git. Use secret scanning; rotate exposed credentials using the responsible account administrator. Store operational secrets in hosting secret management. Never place a secret in a VITE_ variable: those are public build-time values. Authorization cannot depend on hiding frontend controls.

## Verification and deployment
Use focused domain tests for boundaries, unknowns, date precision, comparison scope, and disappearance behavior; adapter tests for mapping, duplicate keys, idempotency and rollback; UI checks for filter reconciliation, navigation and accessibility; security checks for direct anonymous data access, role boundaries and credential absence in client builds. Run responsive checks on desktop/tablet/mobile and embedded/direct views. Release with synthetic smoke data first, then approved data. Keep rollback to the prior app release and successful snapshot, and surface adapter failures without replacing data with zeros.

## Configuration boundary
.env.example is an illustrative future scaffold contract, not an active integration. VITE_ values are public build settings. Server variables are read only by server configuration, validated at startup and never serialized to the client. Keep rule values in a versioned validated configuration object shared by server/domain clients; environment values may seed it. Fail operational startup on missing required timezone/access settings. Auth provider, storage, source mappings, retention, exact brand values, and API configuration remain explicit implementation decisions.

## Phase 1 implementation

`src/domain` contains the typed Phase 1 subset of the normalized contracts, pure selectors and rules. `src/config/rules.ts` validates proposed defaults, including queue reason order. `src/data/repository.ts` defines the asynchronous repository boundary and returns defensive copies of the deterministic synthetic fixture. Unsupported modes and all import mutations fail closed; failed calls retain the prior fixture. Comparison capability is unavailable because no prior comparable snapshot exists. This refusal is not an implemented CSV preview/rollback pipeline.

`src/features/overview` renders the shared filtered snapshot. Reusable filter, table, native modal and settings components live in `src/components`. Hash navigation preserves in-memory filters; settings reset on reload. Browser clients receive only fictional fixtures. There is no server or operational authorization in Phase 1: operational use must remain disabled until protected server-side access and storage are implemented and tested.

## Phase 2 Explorer and CSV evaluation
`src/features/work-orders` implements Explorer, normalized record details and the CSV mapping/preview workflow. Its filters are independent from Overview; both use the same pure domain rules. The page stays mounted across navigation so its selected source and in-memory CSV session remain available without changing Overview data. Explorer CSV calculations use the explicitly supplied dataset timezone; demo timezone remains illustrative.

`src/data/csv.ts` parses bounded UTF-8 comma-separated input and creates a normalized allowlisted candidate. Column mappings and status/priority/approval/assignment mappings are explicitly reviewed. Raw unmapped cells are discarded. Optional issue text must already be redacted; attestation is an evaluation guard, not automated privacy redaction or authorization. No arbitrary source URLs, notes, contacts or vendor-directory attributes are imported.

`CsvSession` holds current/previous CSV snapshots and a single staged candidate in memory. Only the latest unrevoked valid preview can commit; failed/stale candidates leave the successful snapshot intact. SHA-256 content/config identity makes exact replay idempotent. Reviewed mapping objects are canonicalized so key order does not create a false mapping change. Account, report scope, timezone and mapping semantics gate session comparisons. Coverage changes are separate from known-value observations, and missing rows are flagged rather than closed/deleted. Observation timestamps are actual load/detection times, not fabricated source events. No observed-change nudges are inferred from this short session history.

The original demo `DataRepository` remains unchanged. CSV evaluation never joins demo properties/vendors or changes Overview's source. Reloading or clearing Explorer removes all CSV session state; there is no localStorage, IndexedDB, server upload or shared persistence. This is the documented isolated local evaluation workflow, not an operational CSV release. Operational use still requires server-side authentication, importer authorization, protected storage and approved retention before handling private reports.

## Desktop and embedding refinements
The sidebar is the only primary navigation. It is fixed to the current viewport, including an iframe viewport, with a matching full-document navy background and compact short-height behavior. Table pagination uses document vertical scrolling; bounded scrolling remains appropriate for dialogs and genuinely narrow table regions. No postMessage resize protocol or permissive framing policy is introduced without verified portal origins. Local iframe checks prove layout and interaction only, not protected Google Sites authentication/session compatibility.

Record detail links use `src/config/sourceLinks.ts`: the verified-origin list is deliberately empty until owner verification. Existing source URLs are checked for HTTPS, exact permitted origin, malformed values and URL credentials. No record URL is generated, and the CSV normalization boundary still discards arbitrary source links. A future reviewed server adapter must supply verified source URLs; the current UI does not enable an integration or bypass authorization.

## Phase 3 workspace and rule architecture
`WorkspaceProvider` composes the existing CsvSession evaluation adapter with React state. Explorer and Action Center consume its selected demo/CSV source and current CSV snapshot. Source changes and new CSV snapshots remount their source-bound presentation state to prevent stale details/drafts crossing datasets. Overview still consumes the original demo repository and its independent filters. The provider does not add browser storage, a backend, messaging or authorization claims.

`src/domain/actions.ts` provides pure eligibility/recommendation/queue/KPI calculations on normalized records, reusing existing Phase 1/2 rules and sorting. CsvSession exposes a defensive comparable observation pair; no-change eligibility is deliberately restricted to this available window. `messageTemplates.ts` generates contact-free editable plain-text templates. MessageDraft owns per-recipient edits only while its record panel is open. Clipboard output is explicit and handles denial; there is no send capability.

Action detail panels reuse WorkOrderDetails for source fields/coverage/history and insert fact-qualified recommendations plus drafting tools. A local imperative Explorer handle opens the matching scoped ID in the currently selected workspace while preserving Explorer's filters; navigation does not construct a source URL. Verified-origin source-link safeguards remain unchanged. Desktop/iframe and keyboard/dialog checks cover the new workspace. Production Google Sites authentication, protected operational imports and live read-only API capabilities remain separate future prerequisites.

## Phase 4 vendor adapter and workspace
`src/data/vendorRepository.ts` defines the normalized vendor reader/import boundary and a separate `VendorCsvSession`. It reuses the existing bounded CSV parser, validates an allowlist of vendor fields, stages defensive preview copies and atomically replaces the latest normalized directory. Preview revocation/generations reject stale candidates; failed imports preserve current data, exact replay is idempotent, and comparable prior IDs support a missing-since-prior count. No raw CSV/contacts are logged, uploaded, persisted or mixed with demo fixtures.

`WorkspaceProvider` holds independent vendor and work-order evaluation sessions/selections. `VendorDirectory` includes its own DatasetProvenance and explicit verifiedIdentifiers capability. Vendor Watch receives normalized directories/snapshots, not CSV payloads or API endpoints; a future authenticated server API adapter can supply the same contracts. UI joins only exact scoped Vendor IDs under matching account/source mode and confirmed namespace semantics. The relationship is local to Vendor Watch's derived metrics; original work-order snapshots and comparison history remain intact. Overview remains its independent demo.

`src/domain/vendors.ts` shares age, active-status, completion-cohort and Action Center rules. `vendorTemplates.ts` generates request-only drafts from supplied facts. `src/features/vendors` implements directory, details, import and local drafts, reusing native modal/focus and existing shell components. An Action Center handle, analogous to Explorer's, supports exact-record navigation without resetting filters.

This evaluator does not implement server contact-role authorization; only synthetic/approved redacted files are permitted. No operational access guarantee, contact sharing, live API, source write, messaging or production framing policy is introduced.

## Phase 5 intelligence workspaces
`src/domain/insights.ts` and `properties.ts` provide pure source-qualified cohort selection, metrics, property grouping/signals, breakdowns, actual monthly events and conservative observed-load backlog history. They reuse the existing rule and completion functions. Property grouping indexes stable IDs/account relationships and preserves Unknown separately. `reviewSettings.ts` validates independent count/sample thresholds and scorecard measurements without changing Rules. `vendorScorecard.ts` adds evidence/sample qualification without a quality formula. `nextAction.ts` improves recommendation/template context without changing follow-up eligibility.

Properties and Analytics consume WorkspaceProvider's same selected work-order snapshot as Explorer/Action Center. Vendor directory state remains separate and retains its verified join gate. Overview remains its prior independent demo. A source/directory replacement remounts source-bound filters/profiles/drill-downs. The provider holds review settings only in memory; reload resets them. No persisted operational data/configuration, source writes or messaging are added.

`src/features/insights` shares provenance/source selectors, date-cohort filters, accessible record lists, duration/coverage views, review settings and text-backed charts. Properties implements the directory, scoped profile, all available current report records and a separate retained prior-property evidence view. Analytics adds chart drill-downs, report-event trends, comparison tables, at most two real retained load observations and an explicit financial empty state. Native dialogs retain focus containment/return and scroll only where needed. Desktop/iframe layout uses the existing six-tab branded shell.

`financialContract.ts` is an unimplemented future read contract, with no endpoint/credentials/financial scope assumed. Phase 6 can supply normalized snapshots/directories through secure server adapters without rebuilding these views. That phase still needs verified source capability/scope, authentication and role enforcement, protected storage/retention, reliable synchronization/auditing and actual portal access/framing validation. This static evaluator does not establish any of those production guarantees.
